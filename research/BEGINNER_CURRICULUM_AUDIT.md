# Build Quest Academy beginner curriculum audit

Reviewed 23 November 2026. Scope: the Academy prototype, its 13 missions, all 55 Build Quest cards, and the 14 Learn Lab modules that supply its teaching material. This audit compares the learning path and its most consequential technical instructions with primary sources. The lesson files were inspected in the repository. The handbook validator passed, which confirms structure and coverage checks. No beginner pilot, Android capstone build, or exhaustive line-by-line technical verification of every cited page was performed.

## Verdict

**Good foundation for an AI-assisted learner. Incomplete as a course a complete beginner can follow independently from zero to a working Android app.** The path covers the right lifecycle, including access rules, failure testing, accessibility, release, and recovery. The missing piece is continuity. A learner needs to see a small app work early, then build up that same example one skill at a time. Several later proofs also assume actions taught in a later stage.

The source library has 57 concept cards, 42 quiz questions, 24 practice drills, and 28 AI-check prompts. The prototype renders concept cards from all 14 modules and adds two testing cards. It presents 13 practice slots and 39 knowledge-check slots, including the 13 bosses. Those slots include repeats. Its selection logic uses only the first mapped module for most drills, quizzes, and explain-back prompts. Glossary terms, AI output checks, secondary exercises, and lesson provenance are missing from the mobile flow. Project has four free-text milestone notes. The 55 build cards provide instructions and self-checked proofs, but the repository has no runnable native capstone with starter and completed versions. Evidence: `guide/mobile/academy.js`, `guide/learn-data.js`, `guide/learn.js`, and `guide/playbook-data.js`.

## Stage-by-stage result

Stage numbers below follow the Build Quest data, which numbers stages 0–12. The Academy displays those as Missions 1–13.

Teach opening the project folder, using the terminal, reading the first error, and checking prerequisites. Offer compatible Expo Go for the introductory exercise or a development build when the exercise needs project-specific native code. ## Corrections to make before reusing the curriculum

1. **Supabase bill limits.** Stage 3’s Spend Cap and custom alerts conflict with the Stage 11 guidance and current docs. The feature is Pro-only, applies to selected usage items, excludes items such as compute and point-in-time recovery, and does not provide custom threshold alerts. Teach Free and Pro separately. [Official cost control](https://supabase.com/docs/guides/platform/cost-control)
2. **Cloud linking and migrations.** `supabase status` reports the local stack. Verify the linked development project and preview migrations against that target. Replace the generic `DROP TABLE` rollback with a reviewed forward correction or an isolated restore when appropriate. Teach grants, RLS, and migration review before data is introduced. [CLI reference](https://supabase.com/docs/reference/cli/supabase-status) · [Local versus hosted commands](https://supabase.com/docs/guides/local-development/local-and-hosted-projects) · [Migration workflow](https://supabase.com/docs/guides/local-development/cli-workflows)
3. **Project pausing.** The guide promises an API query immediately restores a paused free project. Show the documented dashboard restoration path. [Supabase project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)
4. **Expo and Auth instructions.** Replace blanket claims about SDK 58 requiring a development build with a compatibility check. The Supabase Expo quickstart uses SQLite-backed session persistence, while its React Native Auth quickstart still documents AsyncStorage. Both are examples. Pick and test the specific adapter for the capstone, explain persistence versus encryption, and keep route guards separate from backend authorization. Remove the arbitrary five-second email delivery proof. [Expo Go compatibility](https://docs.expo.dev/troubleshooting/expo-go-version-mismatch/) · [Expo quickstart](https://supabase.com/docs/guides/getting-started/quickstarts/expo-react-native) · [React Native Auth quickstart](https://supabase.com/docs/guides/auth/quickstarts/react-native) · [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/) · [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp)
5. **Words and games that teach the wrong rule.** Change “no API keys inside the app” to “no privileged credentials inside the app.” Explain that the mobile client can call Supabase’s Data API under the user’s permissions. Update the original Learn Lab release game to teach upload before closed test and staged rollout for updates. The Academy already overrides that ordering game, while some build cards still need resequencing. [Supabase grants and policies](https://supabase.com/docs/guides/database/postgres/row-level-security#grants-and-policies) · [Play staged rollouts](https://support.google.com/googleplay/android-developer/answer/6346149)

## The smallest complete beginner path

Use a **Habit Check-in** example or another one-entity app. Give learners visible checkpoints they can compare with their own work.

1. **Run and change one screen.** Open the starter on Android, change text, add sample items, and save a Git checkpoint. Provide a short terminal and editor orientation.
2. **Complete one local journey.** Add a habit, mark it complete, and handle invalid input. Show a worked example, then ask the learner to add a similar action with fewer hints.
3. **Connect real data.** Move the same records to a development Supabase project. Follow one authentication path and prove the app can save and reload data while keeping two users’ records separate.
4. **Make it recover and test it.** Reproduce a failed save, keep the draft, retry safely, and record the result on an installed Android build. Walk through one automated test and one accessibility check.
5. **Prepare one test release.** Sign and upload the same app to a test track, install it from Play, and complete the checks that apply to the account. Keep public release and paid features as separate milestones.

Each checkpoint should ship with a starter and finished version, a short code or file tour, expected output, and a recovery hint. Add a transfer exercise where the learner changes a requirement in their own app and explains how they verified it. Restore the existing AI-check prompts and ask learners to compare AI output against the proof before accepting it. After a delay, bring back selected questions with changed wording or examples, including questions previously answered correctly. This design follows IES recommendations on worked examples interleaved with independent practice, delayed review, and explanatory questions. [IES What Works Clearinghouse](https://ies.ed.gov/ncee/WWC/PracticeGuide/1/Published)

**Readiness decision.** Fix the confirmed instructions and release sequence, then have 3–5 first-time builders attempt the capstone from a clean setup. Record where they need help, whether they can make an independent change, and whether their Android proof matches the expected result. Those observations are needed to decide whether the path is genuinely beginner-ready. The course and prototype were left as reviewed for this audit.
